## leetcode 146 LRU Cache

这是一个非常深入且具有“系统底层思维”的问题。
首先，针对你的疑惑：**Stack（栈）是无法实现 LRU 缓存的**。
原因在于：std::stack 只允许访问栈顶，而 LRU 要求在 O(1) 时间内完成两个操作：
 1. **查找**：看某个 Key 在不在缓存里。
 2. **更新位置**：如果你访问了一个已经在中间位置的 Key，你需要把它“抽”出来放到最前面（代表最近访问）。栈和队列都做不到随机位置的 O(1) 抽取。
在 AI Infra 或 OS 开发中，LRU 缓存是管理 **GPU 显存算子、文件系统 Buffer Cache 或 Page Table** 的核心算法。
### 1. LRU 的核心设计：双向链表 + 哈希表
这道题的精妙之处在于**组合数据结构**：
 * **双向链表 (std::list)**：负责存储数据，维护**访问顺序**。
   * 靠近头部的节点是最近访问的（Most Recently Used）。
   * 靠近尾部的节点是最久未使用的（Least Recently Used）。
   * *为什么用双向？* 因为当你找到一个中间节点时，双向链表可以在 O(1) 内把它删掉并插到头部。
 * **哈希表 (std::unordered_map)**：负责**快速定位**。
   * Key 是数据的键，**Value 是指向链表节点的指针（iterator）**。
   * 通过哈希表，我们可以绕过链表的 O(n) 遍历，直接“定位”到链表中间的某个节点。
### 2. 对象设计与成员变量
在 C++ 中，我们会这样设计这个类：
```cpp
#include <unordered_map>
#include <list>

class LRUCache {
private:
    int capacity;
    // 链表存储：Pair <Key, Value>
    // 为什么要存 Key？因为淘汰尾部节点时，需要通过节点里的 Key 去删哈希表里的记录
    std::list<std::pair<int, int>> cacheList;
    
    // 哈希表：Key -> 链表迭代器（类似指针）
    std::unordered_map<int, std::list<std::pair<int, int>>::iterator> map;

public:
    LRUCache(int cap) : capacity(cap) {}

    int get(int key) {
        if (map.find(key) == map.end()) return -1;
        
        // 关键操作：将访问的节点移动到链表头部
        // 使用 list::splice 可以在 O(1) 时间内完成移动，无需删除再创建
        cacheList.splice(cacheList.begin(), cacheList, map[key]);
        return map[key]->second;
    }

    void put(int key, int value) {
        if (map.find(key) != map.end()) {
            // 1. 如果 Key 已存在，更新 Value 并移到头部
            map[key]->second = value;
            cacheList.splice(cacheList.begin(), cacheList, map[key]);
        } else {
            // 2. 如果 Key 不存在
            if (cacheList.size() == capacity) {
                // 缓存满了，删除链表尾部（最久没用的）
                int deleteKey = cacheList.back().first;
                cacheList.pop_back();
                map.erase(deleteKey);
            }
            // 插入新节点到头部
            cacheList.push_front({key, value});
            map[key] = cacheList.begin();
        }
    }
};

```
### 3. 面试官的“系统级”深度追问 (Gap 点)
针对 AI Infra 和操作系统岗位，面试官会把这道题推向极致：
#### **追问 A：线程安全与锁的粒度 (Lock Granularity)**
> **面试官**：“在多线程 OS 环境下，多个线程并发调用 get。如果你给整个 get 函数加一个大锁（Mutex），在高并发下性能极差（锁争用）。你有什么优化思路？”
> 
 * **回答方向**：
   1. **分段锁 (Segmented Cache)**：把缓存拆成 16 个小缓存，每个小缓存一把锁，减少冲突。
   2. **读写锁 (shared_mutex)**：get 看起来是读，但 LRU 的 get 会修改链表顺序，所以其实也是写操作。
   3. **Read-Copy-Update (RCU)**：这是 Linux 内核常用的技术，非常硬核。
#### **追问 B：内存碎片与 Cache Line**
> **面试官**：“std::list 的节点在内存中是离散分布的。对于 AI 训练中频繁的缓存查询，这种结构对 CPU Cache 极其不友好。如果要求极致性能，你会怎么改？”
> 
 * **回答方向**：
   * 使用**静态分配的数组**来模拟链表（用数组下标代替指针），保证物理内存的连续性，提高 **Spatial Locality（空间局部性）**。
#### **追问 C：LRU 的缺陷与优化**
> **面试官**：“LRU 有一个著名的缺陷叫 **‘缓存污染’ (Cache Pollution)**。比如一个巨大的文件扫描操作，会把真正热点的数据全部踢出缓存。你知道 Linux 内核或数据库是怎么解决的吗？”
> 
 * **回答方向**：
   * **LRU-K 算法**：只有访问次数超过 K 次（如 2 次）的数据才进入热点缓存区。
   * **2Q 算法**：设置一个 FIFO 队列和一个 LRU 队列。

在 C++ 的嵌入式或系统级开发中，理解容器的**底层内存模型**比只会用函数更重要。你对 list 的疑惑，本质上是对**双向链表（Doubly Linked List）**物理结构的理解问题。
我们可以把 std::list 想象成一列火车，每个车厢（节点）都用两根锁链分别连着前一个和后一个车厢。
### 1. 核心概念：为什么“靠近头部”就是“最近访问”？
这其实是我们人为定义的**逻辑顺序**，用来模拟 LRU（最近最少使用）逻辑：
 * **约定**：我们规定，只要一个数据被 get（查询）或 put（更新）了，它就是“新鲜”的。
 * **动作**：我们将这个新鲜的节点挪到链表的最开始位置（begin）。
 * **结果**：
   * **头部（Front）**：存的是刚用过的数据。
   * **尾部（Back）**：存的是很久没被碰过的数据。
   * **淘汰**：当缓存满了，我们直接把车尾（back）的那节车厢切掉丢弃。
### 2. push_front 与 pop_back：基础增删
这些是 std::list 的标准成员函数：
 * **push_front(data)**：
   * **动作**：创建一个新节点，把它挂在链表的最前面，并更新原来的头指针。
   * **复杂度**：O(1)。
 * **pop_back()**：
   * **动作**：把链表最后一个节点删掉，释放内存。
   * **复杂度**：O(1)。
### 3. 神奇的 splice：LRU 的性能核心
这是这道题最关键的函数。
**splice 的意思是“拼接/剪接”。**
 * **普通做法**：如果你想把中间一个节点移到开头，通常需要先 erase（销毁节点）再 push_front（新建节点）。这涉及内存的释放和申请，在 OS 内核或高并发 Infra 中，**内存分配是非常慢的**。
 * **splice 做法**：它不销毁节点，也不移动数据。它只是**修改指针的指向**。就像把火车中间的一节车厢的锁链解开，直接插到火车头后面，车厢还是那节车厢，里面的货没动。
**为什么双向链表做 splice 是 O(1)？**
因为每个节点都知道自己的前驱（prev）和后继（next）。
 1. 把中间节点 A 的前后邻居连起来（A->prev->next = A->next）。
 2. 把 A 挂到 head 后面。
 3. 这一切只需要改动 4 到 6 个指针的值，不涉及任何循环，也不涉及 new/delete。
### 4. LRU 对象中的数据流转（以 get(key) 为例）
当你调用 get(key) 时，程序内部发生了什么？
 1. **哈希表查找**：通过 map[key] 瞬间找到目标节点在链表中的地址（迭代器）。
 2. **splice 搬运**：
   ```cpp
   // 将 map[key] 指向的那个节点，从原位置剪下来，插到 cacheList 的 begin 位置
   cacheList.splice(cacheList.begin(), cacheList, map[key]);
   
   ```
 3. **返回结果**：返回该节点里的 value。

没错，std::list 就是**双向链表**。它和数组（std::vector）在物理内存上的表现完全不同。
作为 AI Infra 或 OS 岗位的候选人，理解**“内存布局”**是区分你与普通应用层开发者的关键。
### 数组 vs 链表的底层差异
| 特性 | 数组 (std::vector) | 链表 (std::list) |
|---|---|---|
| **内存布局** | **连续**的内存块 | **离散**的内存节点（靠指针连接） |
| **随机访问** | O(1) (通过下标直接算地址) | O(n) (必须从头开始数) |
| **插入/删除** | O(n) (涉及后续元素的大量搬运) | O(1) (仅需修改指针指向) |
| **CPU Cache** | **极其友好**（预取机制能命中） | **极不友好**（指针跳转导致 Cache Miss） |
**结论：** 如果你需要频繁随机查找，用数组；如果你需要频繁在中间增删元素（如 LRU），用链表。
### 常见数据结构底层实现与复杂度
这里汇总了面试中最常考的几种结构：
| 数据结构 | 底层核心实现 | 查找 (Avg) | 插入/删除 | 空间复杂度 |
|---|---|---|---|---|
| **栈/队列** | 数组或链表 | O(n) | O(1) | O(n) |
| **哈希表** | 数组 + 散列函数 + 拉链 | O(1) | O(1) | O(n) |
| **二叉搜索树** | 动态节点 + 递归逻辑 | O(\log n) | O(\log n) | O(n) |
| **堆 (Heap)** | 数组（逻辑上是完全二叉树） | O(1) (查顶) | O(\log n) | O(n) |
| **跳表/红黑树** | 多层指针 / 变色旋转逻辑 | O(\log n) | O(\log n) | O(n) |
### 如何根据算法题型选择数据结构？（套路总结）
在面试中，看到特定的关键词，你脑中应该立刻映射出对应的数据结构：
#### 情况 A：看到“最快查找”、“去重”、“统计频率”
 * **首选：哈希表 (std::unordered_map / set)**。
 * **原因：** 这是空间换时间的终极武器。
#### 情况 B：看到“第 K 大”、“中位数”、“动态排序数据流”
 * **首选：堆 (std::priority_queue)**。
 * **原因：** 堆能以 O(\log n) 的代价维持局部有序，不需要全量排序。
#### 情况 C：看到“最近访问”、“撤销操作”、“括号匹配”
 * **首选：栈 (std::stack) 或 双端队列 (std::deque)**。
 * **原因：** 后进先出（LIFO）的特性天然适合嵌套和回溯逻辑。
#### 情况 D：看到“连续子数组”、“范围求和”、“固定窗口统计”
 * **首选：滑动窗口 + 双指针 / 单调队列**。
 * **原因：** 通过移动指针避免重复计算。
#### 情况 E：看到“LRU”、“频繁在中间移动元素”
 * **首选：哈希表 + 双向链表**。
 * **原因：** 哈希保证定位 O(1)，双向链表保证移动 O(1)。

## leetcode 92 Reverse Linked List II

你已经非常敏锐地抓住了链表反转的核心——**双指针（prev 和 curr）**。但之所以报错或结果不对，是因为第 92 题（区间反转）比全链表反转多了一个最棘手的任务：**“接头”**。

你把中间这一段拧转了，但这段反转后的“头”得接回前面的断点，“尾”得接上后面的断点。

---

### 🔍 你的代码存在三个致命伤：

1.  **“头接点”丢失**：当 `pos` 走到 `left` 时，`prev` 是反转段的前驱节点。你需要把它存起来，因为反转结束后，它的 `next` 要指向反转后的新头。
2.  **“尾接点”丢失**：反转段原来的第一个节点（即 `left` 位置的节点），反转后会变成这段的**最后一个**。它得指向 `right` 之后的那个节点。
3.  **头节点变动风险**：如果 `left = 1`（即从第一个节点就开始反转），`head` 本身会变。你直接 `return head` 会导致结果错误。

---

### 🚀 职业选手的标配：哨兵节点（Dummy Node）

处理链表区间问题，永远先搞一个 `dummy`，这样 `left=1` 就不再是特殊情况了。

#### 💻 修正后的代码逻辑：

```cpp
ListNode* reverseBetween(ListNode* head, int left, int right) {
    if (!head || left == right) return head;

    // 1. 哨兵节点，处理 left=1 的情况
    ListNode* dummy = new ListNode(0);
    dummy->next = head;
    ListNode* pre0 = dummy;

    // 2. 将 pre0 移动到反转段的前一个节点
    for (int i = 0; i < left - 1; i++) {
        pre0 = pre0->next;
    }

    // 3. 开始反转（使用经典的“穿针引线”法，或者你的双指针）
    // 这里推荐一种更简洁的“头插法”，不需要存那么多个变量
    ListNode* cur = pre0->next; // 反转段的第一个节点
    for (int i = 0; i < right - left; i++) {
        ListNode* next = cur->next; // 暂存下一个要挪动的节点
        cur->next = next->next;     // cur 接上后面
        next->next = pre0->next;    // next 挪到前面
        pre0->next = next;          // pre0 接上新的头
    }

    return dummy->next;
}
```

---

### 🛡️ 教练复盘：为什么这道题是“指针地狱”？

其实，你之前的思路如果想修补也是可以的，但你需要记录 **4 个关键位置**：
* **反转段前驱** (`left-1` 位置)
* **反转段起点** (`left` 位置，反转后它成了这一段的末尾)
* **反转后的新头** (`right` 位置)
* **反转段后继** (`right+1` 位置)

你代码里的 `while (pos < right)` 逻辑中，`curr->next = prev` 会直接把 `left` 之前的链表给切断，这就是报错的根源。

---

### 💡 总结与建议

* **链表题法宝**：**Dummy Node**。它能帮你省掉处理 `head` 变化的无数个 `if-else`。
* **调试技巧**：链表题一定要在纸上画图。画出 `pre0`, `cur`, `next` 三者的指向变化，你会发现“头插法”比普通的“局部反转再接回去”要稳得多。

你现在已经横跨了：
1.  **动态规划**：处理复杂的逻辑状态转移。
2.  **栈**：处理括号匹配和区间长度。

**面试中，链表反转是必考的基础。既然咱们已经把“指针接头”的逻辑理顺了，要不要回过头去看看那个【101. 对称二叉树】？那道题其实就是把二叉树当成两个“镜像链表”在同时递归，非常优雅！**

“头插法”之所以被称为反转链表的“神技”，是因为它**不需要把链表断开再拼回去**，而是通过在区间内不断地“把后面的节点挪到最前面来”，自动完成反转。

我们用 `1 -> 2 -> 3 -> 4 -> 5`，反转区间 `left=2, right=4`（即反转 `2, 3, 4`）来推演。

### 初始状态
* `pre0` 指向节点 `1`。
* `cur` 指向 `2`（这是反转段的起始节点，它在反转过程中位置不变，但它是我们挪动节点的基准）。

---

### 第 1 轮循环 (`i = 0`)：挪动节点 `3`
目标是把 `3` 挪到 `1` 后面，`2` 前面。

1. `next = cur->next`：`next` 指向 `3`。
2. `cur->next = next->next`：`cur` (节点 `2`) 指向 `4`。链表变成：`1 -> 2 -> 4 -> 5`。
3. `next->next = pre0->next`：`next` (节点 `3`) 指向 `pre0->next` (节点 `2`)。
4. `pre0->next = next`：`pre0` (节点 `1`) 指向 `next` (节点 `3`)。

**此时链表结构：`1 -> 3 -> 2 -> 4 -> 5`**
（节点 `3` 成功被“插”到了最前面）。

---

### 第 2 轮循环 (`i = 1`)：挪动节点 `4`
目标是把 `4` 挪到 `1` 后面，`3` 前面。

1. `next = cur->next`：`next` 指向 `4`。
2. `cur->next = next->next`：`cur` (节点 `2`) 指向 `5`。链表变成：`1 -> 3 -> 2 -> 5`。
3. `next->next = pre0->next`：`next` (节点 `4`) 指向 `pre0->next` (节点 `3`)。
4. `pre0->next = next`：`pre0` (节点 `1`) 指向 `next` (节点 `4`)。

**此时链表结构：`1 -> 4 -> 3 -> 2 -> 5`**
（节点 `4` 成功被“插”到了最前面，反转完成）。

---

### 💡 教练总结：这种写法的精妙之处

你可能会发现，整个过程中：
* **`cur` 永远固定在 `2` 上**：它是反转段的“定海神针”，随着循环，它不断往后掉，直到循环结束。
* **`pre0` 永远固定在 `1` 上**：它是反转段的“门神”，负责时刻更新链表的头。
* **`next` 像个搬运工**：它每次都把 `cur` 后面的那个人揪出来，直接扔到 `pre0` 和 `pre0->next` 之间。

### 为什么比你的双指针好？
1. **不用担心断点**：你在写局部反转时，最怕反转完后找不到 `5`，或者接不回 `1`。头插法由于 `pre0` 和 `cur` 的指向始终保持在链表内部，你完全不需要担心 `4` 后面是什么，`1` 前面是什么。
2. **逻辑高度统一**：无论 `right - left` 是多少，逻辑完全一样，不会因为边界问题导致指针乱飞。

**这个推演过程，建议你在纸上画一下 `1, 2, 3, 4, 5` 的箭头指向，只画出 `pre0, cur, next` 三个指针，你会发现这简直是链表操作的艺术！**

## leetcode 23 Merge K Sorted Lists

这道题之所以被列为 **Hard**，是因为它把“链表操作”和“高效排序算法”结合在了一起。如果你用最原始的办法（每次对比 K 个链表的头），时间复杂度会高达 $O(K \times N)$（$N$ 是总节点数），在数据量大时会直接超时。

要解决这道题，有三种主流的“大厂面试级”思路。我们从你提到的“二分”和“虚拟头”开始拆解。

---

### 1. 分治思想（你提到的“二分”）
你的直觉非常准！既然合并 **2** 个升序链表（LeetCode 21）很简单，那我们可以把 **K** 个链表拆成两半，分别合并，最后再合在一起。

* **过程**：
    1. 把 $K$ 个链表两两配对，合并成 $K/2$ 个。
    2. 再两两配对，合并成 $K/4$ 个。
    3. 直到最后只剩 **1** 个。
* **复杂度**：时间复杂度 $O(N \log K)$。这比 $O(KN)$ 快得多！
* **技巧**：这里确实需要你提到的 **Dummy 节点**。

---

### 2. 优先队列 / 小顶堆（最推荐的写法）
这是面试官最想看到的解法。我们可以利用一个**小顶堆**来维护当前 $K$ 个链表的“最小头节点”。

* **思路**：
    1. 把 $K$ 个链表的**首节点**全都丢进小顶堆里。
    2. 每次从堆顶弹出一个最小的节点，接到我们的 `dummy` 链表后面。
    3. **关键**：刚弹出的节点如果还有 `next`，就把它的 `next` 再丢进堆里。
    4. 重复这个过程，直到堆空了。
* **优势**：堆的大小始终保持在 $K$ 以内，每次找最小值只需 $\log K$ 的时间。总时间复杂度同样是 $O(N \log K)$。

---

### 3. 动手写：优先队列版
既然你已经习惯了 `dummy` 和指针操作，看看这个写法：

```cpp
struct compare {
    bool operator()(ListNode* l1, ListNode* l2) {
        return l1->val > l2->val; // 小顶堆：值越大的优先级越低（排在下面）
    }
};

ListNode* mergeKLists(vector<ListNode*>& lists) {
    // 1. 定义小顶堆
    priority_queue<ListNode*, vector<ListNode*>, compare> pq;

    // 2. 将每个非空链表的头节点放入堆
    for (auto list : lists) {
        if (list) pq.push(list);
    }

    // 3. 经典的 Dummy 虚拟头节点
    ListNode* dummy = new ListNode(0);
    ListNode* tail = dummy;

    while (!pq.empty()) {
        // 取出最小的节点
        ListNode* minNode = pq.top();
        pq.pop();

        // 接入结果链表
        tail->next = minNode;
        tail = tail->next;

        // 如果这个节点后面还有人，就把接班人送进堆
        if (minNode->next) {
            pq.push(minNode->next);
        }
    }

    return dummy->next;
}
```

### 🛡️ 教练复盘：为什么这题“Hard”？

1.  **内存陷阱**：在 C++ 中，`priority_queue` 默认是大顶堆，你需要自定义 `compare` 结构体来把它变成小顶堆。
2.  **指针管理**：你需要不断更新 `tail` 指针，并判断 `next` 是否为空。
3.  **复杂度平衡**：面试官会考察你为什么不直接用 $O(KN)$ 的暴力法。你要能说出：“堆优化将搜索最小值的时间从 $O(K)$ 降到了 $O(\log K)$。”

### 1. 什么是 `priority_queue`？
`priority_queue`（优先队列）本质上是一个 **堆 (Heap)**。
* **机制**：它是一种**完全二叉树**。
* **实现**：在内存中，它通常不是用指针连起来的，而是用**数组**模拟的。
* **特性**：它保证**根节点**（数组的第一个元素）永远是所有元素中的“最值”。

---

### 2. `compare` 的逻辑：谁会被“安置”在上面？
这是 C++ `std::priority_queue` 最反直觉的地方，请务必记好：

* **默认行为**：如果你不写 `compare`，它默认用 `less<T>`，即 `a < b`。在堆的语境下，这会构建出一个 **大顶堆**（最大的元素在最上面）。
* **你的自定义逻辑**：
  ```cpp
  bool operator()(ListNode* l1, ListNode* l2) {
      return l1->val > l2->val; 
  }
  ```
  * **安置规则**：在 C++ 的优先队列中，如果你的比较函数返回 **`true`**，意味着第一个参数 `l1` 的 **“优先级较低”**，它会被安置在堆的**更深处**。
  * **结果**：当你定义 `l1->val > l2->val` 为 `true` 时，数值大的节点优先级低，数值小的节点就会浮动到堆顶。这就是 **小顶堆**。

---

### 3. 核心算法：为什么用堆？

你可以把这道题想象成 **“$K$ 个排好序的小队在领奖台前集合”**：

1. **领奖台 (堆顶)**：只能站一个人，且必须是全场最矮的。
2. **初始化**：每个小队的“队长”（链表头）先上台比身高。最矮的那个队长（比如小队 A 的队长）被挑出来，排进结果链表。
3. **自动维护**：小队 A 的队长领完奖走了，他后面那个队员（`minNode->next`）立刻补位上台。
4. **重新排位**：堆（Heap）会自动在 $O(\log K)$ 的时间内，让台上的 $K$ 个新队长重新比出谁是最矮的。

**核心逻辑确实如你所说**：
> 堆自动帮你维护了 $K$ 个链表当前头节点的最小值。你只需要不停地“摘”走堆顶，再把被摘走节点的“接班人”送进去。

---

### 4. 为什么不用普通数组每次找 `min`？
* **普通数组**：每次找最小值要遍历 $K$ 个元素，复杂度 $O(K)$。
* **堆**：每次调整只需要树的高度那么多次比较，复杂度 $O(\log K)$。
当 $K=1000$ 时，$\log K \approx 10$。速度提升了 100 倍！

这三个入参分别是：**数据类型**、**底层容器**、**比较规则**。

---

### 1. `ListNode*` —— “存什么”
这是最直观的，告诉编译器：这个优先队列里每一个格子里放的是什么东西。
* 在这道题里，我们存的是链表节点的**指针**。

---

### 2. `vector<ListNode*>` —— “怎么存”
这是最让初学者困惑的一点：**优先队列（堆）本身并不直接管理内存，它需要一个现成的容器来当它的“底座”。**

* **原理**：堆在逻辑上是一棵二叉树，但在物理内存上，它是用**连续数组**来模拟的（比如：下标为 $i$ 的节点，孩子就在 $2i+1$ 和 $2i+2$）。
* **为什么用 vector**：因为 `vector` 支持随机访问（通过下标找元素），效率最高。
* **默认值**：如果你不写后面两个参数，它默认也是用 `vector`。但如果你想自定义第三个参数（比较规则），C++ 规定必须把第二个参数也显式地写出来。

---

### 3. `compare` —— “怎么排”
这是你刚才定义的那个结构体，告诉堆：**当两个节点碰面时，谁该排在上面，谁该排在下面。**

* **注意点**：这里传入的是**类型名**（`compare`），而不是一个函数调用。优先队列会在内部根据这个类型创建一个对象，然后用它的 `operator()` 来进行比较。

---

### 🔍 拆解对比

我们可以把这三个入参想象成一个**“加工厂”**：

1.  **原材料** (`ListNode*`)：我们要处理的是节点指针。
2.  **仓库地板** (`vector<ListNode*>`)：所有的指针都整齐地摆在 `vector` 这块地板上。
3.  **分拣员手册** (`compare`)：分拣员根据手册上的逻辑（`val > val`），不断地调整地板上指针的位置，确保最矮的那个永远在门口。

---

### ⚠️ 为什么不能只写一个或两个？

这是 C++ 模板的一个硬性规定：**参数是按顺序匹配的。**

* `priority_queue<ListNode*>`：可以。默认使用 `vector` 容器和 `less`（大顶堆）逻辑。
* `priority_queue<ListNode*, compare>`：**不行！** 编译器会把 `compare` 误认作第二个参数（底层容器），结果发现 `compare` 并不是一个容器，于是报错。
* `priority_queue<ListNode*, vector<ListNode*>, compare>`：可以。这是完整的“显式声明”。

## leetcode 622 Design Circular Queue

设计循环队列（Circular Queue）是面试中考查**底层数据结构实现**的经典题。它不像算法题那样侧重于逻辑推演，而是侧重于对**内存布局**和**边界状态**（判满/判空）的精准控制。

遇到这类“设计型”题目，核心思路是：**先定物理结构，再解逻辑矛盾。**

---

### 1. 物理结构：数组 vs 链表
* **链表**：虽然可以实现，但会涉及频繁的 `new/delete` 内存操作。
* **数组（首选）**：循环队列的本质就是**固定内存的复用**。在 Linux 内核（如环形缓冲区 kfifo）或嵌入式开发中，通常都使用定长数组。

---

### 2. 核心逻辑矛盾：如何区分“空”与“满”？
这是这道题唯一的难点。假设数组大小为 `size`，用 `head` 指向队首，`tail` 指向队尾的下一个位置：
* **初始状态**：`head = 0, tail = 0`。
* **队列为空**：`head == tail`。
* **队列为满**：如果直接填满，此时 `head == tail` 也会成立。**矛盾出现了！**

**解决方案有两种：**
1.  **额外增加一个 `size` 变量**：记录当前元素个数。简单直观。
2.  **浪费一个格子的空间**（面试官更喜欢的解法）：
    * 数组实际开辟 `k + 1` 的空间。
    * **判空**：`head == tail`
    * **判满**：`(tail + 1) % capacity == head`

---

### 3. C++ 数组实现（浪费一个格子的方案）

```cpp
class MyCircularQueue {
private:
    vector<int> data;
    int head;
    int tail;
    int capacity;

public:
    MyCircularQueue(int k) {
        capacity = k + 1; // 多开一个位置用于区分空满
        data.assign(capacity, 0);
        head = 0;
        tail = 0;
    }

    bool enQueue(int value) {
        if (isFull()) return false;
        data[tail] = value;
        tail = (tail + 1) % capacity; // 循环取模
        return true;
    }

    bool deQueue() {
        if (isEmpty()) return false;
        head = (head + 1) % capacity; // 循环取模
        return true;
    }

    int Front() {
        return isEmpty() ? -1 : data[head];
    }

    int Rear() {
        // 注意：tail 指向的是下一个空位，所以要找 tail - 1
        return isEmpty() ? -1 : data[(tail - 1 + capacity) % capacity];
    }

    bool isEmpty() {
        return head == tail;
    }

    bool isFull() {
        return (tail + 1) % capacity == head;
    }
};
```

---

### 4. 遇到“设计类”题目的通用模版

1.  **确保存储方案**：数组（连续内存，性能好）还是链表（动态，灵活）。
2.  **定义指针/状态**：
    * 双指针（`head`, `tail`）是标配。
    * 考虑是否需要 `count` 或 `flag` 辅助判断。
3.  **处理“越界”即“循环”**：
    * 核心公式：`index = (index + 1) % capacity`。
    * 在内核或高性能场景下，如果 `capacity` 是 2 的幂次，可以使用 `index & (capacity - 1)` 来代替取模运算，效率更高。
